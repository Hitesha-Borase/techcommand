## Implemented behavior

- **Technician portal → Route → Plan my route → Get Google estimates.** The technician chooses stop order, start address, time on site and optional return destination. On-site defaults and manual plan/GPS controls are preserved.
- Protected `/api/dispatch/estimate` GET reports configuration only; POST calls the official Google Routes REST endpoint from the server. No SDK or new dependency. No database migration.
- The server derives service addresses from the authorized saved jobs. The submitted address is only a stale-display check, never authority to substitute a different job address. It verifies route ownership, technician company/user, every current assignment, account/facility hierarchy, complete stop set, route version and addresses before requesting Google, then checks membership, assignments and route again before returning results.
- Chosen order is preserved. Up to 75 stops plus return are split into consecutive requests with at most ten intermediate waypoints each. Each leg appears once across chunk boundaries. This does not optimize stop order or use Google's Route Optimization API.
- Driving estimates use `TRAFFIC_UNAWARE`; they exclude current/predicted traffic. The panel shows drive minutes, technician-entered on-site time, estimated total, projected arrivals/finish and optional return. Google warnings are preserved as escaped text. Times round up to whole minutes.
- Missing setup, paused integration, invalid addresses, stale assignments, limits, timeout, unreadable/incomplete replies and partial multi-request failure show a recoverable message. Partial results never appear as a complete plan.
- The Google panel is separate from saved manual estimates. No Google duration, warning or result is written to the saved route, browser storage, service worker, invoice, payroll, audit JSON or offline queue. Results remain in active component memory only and clear on route/address/order changes, navigation, session recovery or unmount. Recalculate after reopening. Existing manual plan persistence is unchanged.
- Google Maps attribution and links to Google's terms/privacy are included. No Google result is plotted on a non-Google map or sent to Apple/Waze; GPS links continue to use the company's/user's own addresses.
- Requests send addresses and routing options only. Work-order IDs, customer names, job descriptions, technician identity, medical records, photos and notes are not included in the Google request. No raw provider error body is logged or returned. The panel is excluded from PostHog capture; version-86 client privacy controls are preserved; backend hardening remains P0-03b.

## Usage and recovery

Default server limit: **100 reserved Google API requests per company per UTC day**, and one calculation per route per 60 seconds. One calculation can require multiple API requests on long routes; the whole possible count is reserved atomically before calling Google. Failed attempts consume the reserved allowance conservatively. This is an application request limit, not a dollar budget or control over other applications using the same Cloud project/key.

`GOOGLE_ROUTES_DAILY_REQUEST_LIMIT` optionally changes the application limit to an integer from 1 to 1000. Invalid configuration falls back to 100. Use Google Cloud quotas as an independent safeguard; billing alerts alone do not stop spending. Review the actual account's applicable price/SKU before enabling live calls.

Existing `integration_events` records hold the route ID, status, reserved request count, mode and sanitized error code only. No new table, migration or automatic processor. Successful responses produce a real processed event. Failed requests cannot be replayed through Integration Center's queue button: the technician must request a fresh calculation with current authorization and addresses. A saved administrator pause stops requests, including a pause made while a lookup is running.
